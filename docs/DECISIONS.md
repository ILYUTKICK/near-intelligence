## ADR-018 — NI-038 prototype outcome: Tiptap adoption confirmed (2026-11-07)

**Context:** ADR-005 chose Tiptap with an explicit gate — the NI-038 prototype had to prove that typing, undo and JSON serialization survive custom React node views before the editor build depends on it.

**Outcome (confirmed):** the prototype (`apps/web/src/features/editor/prototype/`) implements two atomic custom nodes (chart block with node-view controls, insight card with a nested-editable title input) and asserts via tests: node-schema JSON round trip is identical after reload; typing/undo survive React node updates; editor commands (`undo`) escape from inside node views; an empty document parses validly. Node views use `contentEditable=false` islands with a nested editable input — the pattern for NI-039/NI-041 evidence nodes.

**Constraints verified:** Tiptap normalizes an empty document to one empty paragraph (doc schema requires block content — the canonical JSON must expect it); adjacent inserts may group into one history step (undo tests must not assume per-command granularity); `renderHTML` must return the tuple form and serialize attrs as data-attributes for HTML-level fidelity, while the canonical storage path is JSON (NI-036).

**Alternatives / consequences:** no custom rich-text engine was considered (ADR-005 stands); BlockNote not re-evaluated — the gate passed, so switching cost is unjustified. Next: production nodes bind to NI-031 chart registry entries (no synthetic fixtures) and NI-032 datasets.

## ADR-019 — NI-033 dependency: Apache ECharts 6.1.0, modular SVG renderer, no React wrapper (2026-11-08)

**Context:** ADR-006 chose "ECharts through one chart adapter" over Recharts, with a table fallback, but no concrete package/version existed. NI-033 must add the real dependency, align the renderer with the NI-031 registry `renderer_version` (`echarts-modular-svg@1`) and keep the frozen-export path (NI-057) able to reuse the same option builder in Node.

**Decision:** adopt `echarts` **6.1.0** in `apps/web` — the npm registry `dist-tags.latest` at the time of selection (published 2026-05-19, so pnpm's `minimumReleaseAge` supply-chain window has long cleared), Apache-2.0, runtime dependencies limited to `zrender` 6.1.0 and `tslib` 2.3.0. Only modular entry points are imported (`echarts/core` plus `LineChart`/`BarChart`/`ScatterChart` from `echarts/charts`, `Grid`/`Tooltip`/`Aria` from `echarts/components`, `SVGRenderer` from `echarts/renderers`) to keep the bundle bounded; the full `echarts` bundle import is not used. The SVG renderer (not canvas) is the documented default: SVG keeps plotted text as DOM (screen-reader/export friendly) and matches the registry's renderer capability string.

**Structure consequence:** there is no React chart wrapper. A pure typed option builder (`features/charts/renderer/option-builder.ts`) converts the generated `ChartViewResponse` into a JSON-safe `EChartsOption`; the React `ChartView.tsx` only mounts ECharts lazily, feeds it the built option, cancels stale requests and disposes on unmount. The same builder is callable from Node without DOM/browser globals, which is what the NI-057 static export (`apps/web/scripts/render-charts.mjs`) must reuse instead of growing a second renderer.

**Numeric decision (recorded, tested):** decimal strings from the API are the only source of exact values — the accessible table and tooltip formatters render the original strings (with grouping separators, bound labels and gap reasons). Parsing to `Number` happens only for plot coordinates (axis positioning), where a 29+ significant-digit yocto-scale value intentionally loses digits that only affect sub-pixel position. This is the documented float boundary of ADR-014 for rendering; no financial aggregation ever happens in the renderer.

**Alternatives / consequences:** Recharts — rejected in ADR-006 (React-coupled, no panel/scatter depth, no Node SSR story); Chart.js — canvas-first, weaker labeling/accessibility and panel layout for this purpose; uPlot/lightweight-charts — too narrow (time-series/finance) for panels/bounds labeling. Version alternatives: echarts 5.6.0 (2024-12) is the previous major; 6.0.0 (2025-07) → 6.1.0 is its stable successor and the maintained `latest`, so pinning 5.x would immediately lag the maintained line. Consequence: the registry definition carries `renderer_version: "echarts-modular-svg@1"`; the renderer module exports the same constant and refuses to render a definition pinned to a different renderer capability set (honest unsupported-renderer state, never a best-effort redraw). Upgrades of echarts require a registry decision only if the capability set changes, because definitions pin the capability, not the npm version.

**Verification:** version/license/integrity taken from the npm registry (`npm view echarts version dist-tags license` — `6.1.0`, `latest`, Apache-2.0; package entry `exports` inspected for `./core`, `./charts`, `./components`, `./renderers`, `./ssr/client`); frozen-lockfile install diff contained to echarts/zrender/tslib; renderer tests cover gaps, bounds, large decimals, range-change metadata survival and dispose/cleanup.

## ADR-021 — Revocable read-only sharing of one frozen revision (2026-11-12)

**Context:** NI-060 requires explicit, revocable read-only publication of one acknowledged document revision, separate from private drafts and private UUID routes (ADR-020 consequence). The existing frozen machinery is private-plane: the NI-056 export IR carries private editorial data (owner id, author identity, annotation authorship timestamps, evidence explanations, the full internal UUID graph — document/version/insight/hypothesis/evidence ids), so it cannot be published as-is. AGENTS.md prohibits public caching of private content, and AUTHENTICATION_SECURITY forbids private content or session tokens in URLs/analytics/errors. A share is content the owner deliberately publishes to token holders — a new capability pattern the database has not had yet.

**Decision:** one publication plane, three boundaries.

*Token capability.* A share link carries a high-entropy capability token (`secrets.token_urlsafe(32)`, 256 bits, URL-safe) in the PATH segment only (`/share/{token}` on the web, `/api/shares/{token}` on the API) — never a query parameter, never analytics, never an error message, never a log line. The database stores only the SHA-256 digest of the token (`varchar(64)` with a format CHECK, unique index); the raw token is returned exactly once in the create response and never persisted. Every share response (projection, chart view, CSV) is `Cache-Control: no-store` with `Referrer-Policy: no-referrer`; there is no signed URL and no immutable-cache reuse (unlike public-by-design chart data). Unknown, expired, revoked and malformed tokens all return the ONE generic `404 NOT_FOUND` envelope — no oracle distinguishes them.

*Allowlisted projection.* The published payload is a DISTINCT narrower model (`ShareProjection`, `share_projection_version = 1`), built as a pure narrowing transform of the verified NI-056 export IR inside the create transaction: chart evidence is resolved exclusively through the NI-043 historical resolver (fail-closed, never latest data), public references (model runs, citations, dataset versions) are validated before publication. Excluded: owner id, author identity, document/version/insight/hypothesis/evidence/target private UUIDs, annotation authorship/modified timestamps, evidence explanations, snapshot ids. Kept: title, revision, revision `created_at`, content SHA-256, schema version, block ids (needed to address chart blocks), public-safe chart pins (chart definition version, dataset version, selection, frozen `ChartViewResponse`), dataTable columns/rows/dataset references, rich text, insight/hypothesis content, risk cards, sanitized source id+name, model run public references, citation artifact ids, and a deterministic limitations line. The owner dialog renders exactly this projection as the preview and the create request must carry its canonical-bytes SHA-256; the server rebuilds the projection in the create transaction and refuses (409) when the consented hash does not match what would actually be published — preview and publication cannot diverge.

*Storage and RLS (migration 0017).* One new table `app.document_shares`, FORCE RLS, holding the frozen projection canonical bytes (`bytea`) with `projection_sha256`/`projection_byte_size` (32 MiB cap, pairing CHECKs) under the same composite same-owner FKs as 0012 (`(document_version_id, document_id, owner_id) → app.document_versions`, CASCADE). Three near_app SELECT policies (permissive, OR-combined): the owner policy (`owner_id = app.current_user_id() AND app.identity_is_active()`); the token policy (`app.current_user_id() IS NULL AND status = 'active' AND (expires_at IS NULL OR expires_at > now())`) — the no-identity guard means an authenticated session can never read another user's share through it, and revoked/expired rows are invisible even to raw no-identity SQL. INSERT/DELETE are owner-only; UPDATE is owner-only and column-granted to (`status`, `revoked_at`, `updated_at`, `projection`, `projection_sha256`) with the structural CHECK `(status = 'revoked') = (projection IS NULL)`: revocation always clears the bytes (export-sweep semantics) and no path can rewrite the bytes of a live share. `near_operator` holds purge-only power (the saved_charts precedent): a lifecycle-columns-only SELECT (required by the purge WHERE, never token hashes or bytes) plus DELETE; `near_public` has nothing. The UPDATE grant is column-scoped (status, revoked_at, updated_at and the three projection columns only — no table-wide grant), so token_hash and the identity columns carry no UPDATE grant for any runtime role. Expires_at is optional (NULL = no expiry) and denial is computed live on every read (RLS policy + service re-check per request), like the export job's honest read-time state; no sweeper is required for correctness.

*API surface.* Owner-scoped (`get_principal` + `principal_transaction`, no-store): `POST /api/documents/{document_id}/shares` (consent payload naming the acknowledged revision and visible scope, `Idempotency-Key` replay), `GET /api/documents/{document_id}/shares/preview` (the exact projection + its hash), `GET /api/documents/{document_id}/shares` (owner list: id, revision, lifecycle status computed at read, created/expires/revoked — never the token), `DELETE /api/documents/{document_id}/shares/{share_id}` (revoke). Token-gated (no identity, no-store, generic deny): `GET /api/shares/{token}` (projection), `GET /api/shares/{token}/charts/{block_id}/view` (frozen view), `GET /api/shares/{token}/charts/{block_id}/csv` (exact-value CSV derived deterministically from the frozen view, same serializer semantics as the historical revision CSV). Each public request re-checks live state; a share grants no draft/history/list/search/write/export access — the token resolves to exactly one frozen projection and its chart assets.

*Viewer.* `/share/[token]` is a server-rendered read-only page (robots noindex, no-store fetches): static rendering of the projection blocks (never the Tiptap editor), charts via the controlled-view `ChartView` (no loader, no refresh, no latest data), exact-value tables, sanitized source links, model-run/source registries, limitations. It exposes no workspace chrome, no links into private routes and no export beyond the rendered assets. Static SVG/ZIP rendering remains the export pipeline's domain; share assets are the frozen view and its derived CSV, rendered client-side from the projection.

**Threat model (summary):** adversaries are (a) another authenticated user (Bob) — gains nothing: RLS owner policies hide foreign rows even when active, share ids under foreign documents are the generic 404, and the token policy is voided by any transaction-local identity; (b) a token holder — gains exactly the consented frozen projection and its assets, no ownership change, no write, no metadata beyond the allowlist, and loses everything on revoke/expiry on their next request; (c) an unauthenticated stranger without the token — 256-bit entropy makes guessing infeasible and every failure is one generic 404; (d) accidental leakage vectors — token only in the path segment, `no-store` + `Referrer-Policy: no-referrer` on every share response, token never logged (static-sinks scan stays green), hashes only in the database, operator credential cannot read token hashes or bytes; (e) content drift — edits, renames and dataset publications after create never reach a stored projection (bytes are frozen at create; no refresh path exists).

**Alternatives / consequences:** reusing the export IR as the published payload — rejected: it carries private metadata and the full private UUID graph. Signed/expiring share URLs — rejected: AUTHENTICATION_SECURITY records the no-signed-URL rule for private bytes and a signature cannot be revoked server-side per request; live-state checks can. Signed-URL-with-server-state is redundant complexity over the hash lookup. Two-table design (separate token-access table) — rejected: the no-identity guard in one table gives the same isolation without duplicating bytes. Revocation by DELETE — rejected: the owner list must keep revoked history with status; the structural CHECK keeps revoked rows byte-free. Requiring expiry — rejected: owner consent may be open-ended; revocation is the primary control. Trigger-enforced byte immutability — unnecessary: the pairing CHECK plus the column-scoped owner UPDATE grant and the absence of any service write path to live bytes cover the contract, and the probes prove it.

**Scientific/security effect:** a share is a quantitative publication and inherits the publication rules — every chart carries source ids, definition version, dataset version and quality status from the frozen view; missing data stays explicit (null + reason), nothing is zero-filled; the limitations line states the frozen scope. Security effect: the capability model is additive to (not a replacement of) the ownership model — no private route becomes public, and the projection is immutable by construction.

**Affected contracts:** API_SPECIFICATION (share routes and rules), DATABASE_SCHEMA (document_shares), generated OpenAPI client (packages/shared-types), AUTHENTICATION_SECURITY (capability-token rules), FEATURE_SPECIFICATIONS F17, migration 0017 with rollback (drop table).

**Migration/rollback:** 0017 creates the table/policies/grants; downgrade drops it (no backfill, no data migration). Rollback removes the sharing surface entirely; private documents are untouched.

**Verification (recorded 2026-11-12, implemented):** disposable-cluster DB suite — 27 discovered suites / 487 integration tests OK, zero skips (`scripts/run-db-tests.py`, PostgreSQL 18), including the new `test_shares.py` (10 tests: full create→read-as-anonymous/Bob→revoke→deny matrix, idempotent replay never re-emitting the token, consent mismatches, frozen publication across rename/revision/dataset refresh, expiry denials + honest owner list, foreign-management 404 matrix, no-private-access, mutated-pin fail-closed 422, share headers, migration 0017 round trip + SQLAlchemy mirror `alembic check`) and `tests/security/test_security_shares.py` (14 tests: HTTP capability matrix with byte-equal generic denies + projection key-walk against private identifiers; direct RLS probes — capability plane reads live rows only by digest, voided by any identity, expired/revoked invisible, guard-trigger byte immutability, column-scoped UPDATE grants, purge-only operator, cascade). Offline discovery 684 tests OK (255 cluster-gated skips). Web: 53 files / 549 tests pass, including the new share-dialog (8), share-viewer (5) and shares-gateway (5) suites; lint 0 problems, strict TypeScript clean, production build, `check:contracts` current, `check:doc-links` 807 links, `check:contrast` pass, `check:client-secrets` OK (static-sinks AST scan green over the new modules — the raw token appears in no log call).
## ADR-022 — Deterministic advisory integrity checks and the optional grounded-commentary adapter boundary (2026-11-12)

**Context:** NI-065 requires local evidence assistance that verifies document metadata deterministically while keeping interpretive suggestions advisory, plus an optional AI commentary tool. The owner handoff v2 (12 November 2026) supersedes the former plan-only card and requires working tools before deployment, but external model use stays optional and separately configured/authorized; no provider account, purchase or private-document transmission is authorized by this task. Save-time validation already blocks broken same-document links, unapproved dataset pins and unverified insight contexts at write time, so a post-save read-only check surface reports the conditions that genuinely arise after a save: a newer approved dataset version existing for a pinned chart (stale context), a pinned chart definition or public evidence target that became unavailable after the revision was acknowledged, resolved contexts that went missing or invalid for a saved chart block (corruption signal), and pinned data blocks that carry no supporting evidence link (uncited pinned data).

**Decision:** add a read-only `near_api.integrity` package with one owner-scoped route, `GET /api/documents/{document_id}/integrity` (optional `version_id` for historical checks, labeled `is_acknowledged:false` in the response), that parses the acknowledged (or requested) immutable revision and reports typed, advisory findings — each with a stable check id, an advisory severity (never a truth score), the exact block/entity/version/context references and a jump target. The checks write nothing; a rerun is a new GET, so the endpoint is deterministic per revision content. Suggestions can never invent numeric results (findings carry only ids, counts and references), never change pins/coefficients and never trigger mutations — the editor refresh action stays the user's explicit step on the chart block. The optional adapter is a separate `near_api.ai` package with `POST /api/documents/{document_id}/grounded-commentary`: it accepts ONLY explicitly selected context (bounded block ids, resolved/model contexts and prose caps read from the acknowledged revision), builds a bounded prompt over exactly that context, calls the configured provider over an isolated httpx client with the finalized-header refresh bounds (no redirects, no environment proxy trust, byte cap, typed failures, provider error bodies never surfaced), and returns advisory commentary where numbers may only be echoed from the provided context (tagged as quoted). Configuration is a frozen `AICommentarySettings` section defaulting OFF (`NEAR_AI_COMMENTARY_ENABLED=false` plus endpoint/model/key vars read server-side only); when disabled the key is never read or validated and the endpoint returns the typed `unavailable`/`adapter_disabled` state, never fabricated text. Hostile document content passes through as inert quoted material (no instruction interpretation); the API key never appears in logs, responses or error bodies.

**Alternatives / consequences:** running checks at save time only — rejected, save-time rules already cover write-time conditions and the genuinely advisory states (data drift, target unavailability) appear after the save; a background re-check daemon — rejected (no scheduler in MVP and rerun is free as a GET); client-side-only checks — rejected (owner isolation and revision pinning must be server-enforced, and the evidence panel already showed the divergence cost of duplicating state client-side); auto-rewriting or auto-refreshing on findings — rejected, EDITOR_SPECIFICATION makes fresher data an explicit decision. Streaming provider responses, multi-turn conversations and provider-side embeddings — rejected for this bounded MVP scope (one bounded request/response per commentary call). Consequence: findings are always consistent with one immutable revision row, so an acknowledged-revision check cannot race a save; historical checks are advisory-only reads of frozen rows.

**Scientific/security effect:** findings distinguish "newer approved data exists" from "evidence no longer resolves", with exact `context_hash`/dataset/definition ids, so a reader can see whether a published revision was written against different evidence than current data — without any numeric claim of its own. Prompt content is bounded to owner-selected context; no unapproved context leaves the machine (default OFF, operator-configured endpoint only); owner isolation follows the shared one-generic-404 rule; the commentary endpoint is read-only so an adapter failure cannot corrupt a revision, and checks/editing/save/export stay fully usable with the provider down or unconfigured.

**Affected contracts:** new integrity response models and the commentary request/response models registered in the OpenAPI contract set; generated TypeScript client regenerates from the OpenAPI schema (`packages/shared-types`); `AICommentarySettings` in `near_api.settings`; gateway allowlist gains the two same-origin segments; EDITOR_SPECIFICATION gains the advisory findings section, API_SPECIFICATION gains the two endpoint rows, FEATURE_SPECIFICATIONS records the F18 note. No database migration: checks read existing `document_versions` rows, registry and dataset tables only.

**Migration/rollback:** none required (no schema change; new modules are additive). Rollback is removing the router registrations and settings section; stored revisions are untouched. The commentary endpoint is inert (typed `unavailable`) unless the operator explicitly sets the enabling configuration.

**Verification:** deterministic oracle fixtures — a clean document returns zero findings; a stale-context document returns exactly the stale finding with the pinned block id and newest approved dataset id; an uncited pinned chart returns the advisory uncited finding; a drifted public evidence target and a missing resolved context are reported, never silently swallowed; a historical version check reports `is_acknowledged:false`. Two-user ownership: a foreign document is the byte-equal generic 404. Adapter tests run against isolated `httpx.MockTransport` only — success, provider failure, disabled configuration (no call happens) and editing/export remaining functional during adapter failure; prompt-builder unit tests prove only selected context is included; a prompt-injection document passes through as quoted content; secret tests assert the key never reaches logs, client responses or error bodies. No real provider connectivity is claimed from fixtures.
