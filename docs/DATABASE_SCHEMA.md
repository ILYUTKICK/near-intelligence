# Database schema

Logical PostgreSQL schema. NI-003 implements the initial identity tables and role/RLS foundation; remaining domain tables below are specifications for their owning tasks. See [database setup and checks](DATABASE_SETUP.md), [editor](EDITOR_SPECIFICATION.md), [API](API_SPECIFICATION.md), [security](AUTHENTICATION_SECURITY.md).

## Global conventions

Use UUID primary keys unless a stable catalog ID is specified. `created_at`/`updated_at` are non-null TIMESTAMPTZ UTC, server-generated on mutable entities. Immutable entities have created_at only and are update-protected to the runtime role. Direct deletion of scientific artifacts is restricted; private revision projections may be removed only by an ownership-checked parent-document deletion cascade. Dates represent UTC day boundaries, intervals `[start_date,end_date)`. All FKs indexed unless covered by a leading PK/unique index. Strings have bounded lengths; enums use checked text with versioned migrations.

Raw amounts are decimal digit strings in raw artifacts and NUMERIC(78,0) where normalized; derived amounts NUMERIC(78,30), with metric-specific overflow/scale checks before insertion. Preserve more precise original calculation strings in versioned artifacts; never silently truncate and call them exact. API uses decimal strings. Statistical coefficients may be finite float64 in model JSON with explicit numeric policy; reject NaN/Infinity. Hashes are lowercase SHA-256 hex (64 chars), calculated from canonical bytes.

Private rows carry `owner_id REFERENCES users(id)`. Public scientific definitions/data have no owner and are not editable by ordinary users. Composite FKs enforce same-document/same-owner references. RLS uses transaction-local verified application identity plus explicit service predicates; no reliance on frontend filtering.

**Canonical content rule:** `document_versions.content` contains the complete editor JSON, including notes/hypotheses/evidence attributes. Relational block/insight/hypothesis/evidence tables are validated projections of that revision created in the same transaction. Insight, hypothesis and evidence REST mutations rewrite the appropriate nodes and create a new document version through the same service. Old versions retain exact original text, links and pins. APIs default to `current_version_id`.

**Implemented (NI-072, migration `0014_document_organization`):** `app.document_organization` implements the lightweight private organization row exactly as the table above specifies, following the 0002/0011 pattern: composite FK `(document_id, owner_id) → documents(id, owner_id) ON DELETE CASCADE` so deleting a document removes its organization state while the immutable revision chain is untouched; FORCE RLS pairing `owner_id = app.current_user_id()` with `app.identity_is_active()` for near_app (SELECT/INSERT/UPDATE/DELETE), the operator purge-only DELETE, and no grants/policies for `near_migrator`/`near_public`. Column-specific grants: near_app INSERTs `(document_id, owner_id, tags, favorite)` and UPDATEs `(tags, favorite, updated_at)` only — the owner/document identity is never writable. Tags are private metadata, NOT scientific content: nothing in this table feeds `document_versions`, export IRs or public output unless an owner explicitly exports it as metadata. The `BEFORE UPDATE` trigger advances `updated_at` only when `tags`/`favorite` actually change, mirroring the 0011 recency pattern; it never touches `app.documents`, so tagging cannot reorder or re-date the owner's list.

Editor UI undo/redo is local until saved. A failed validation rolls back the entire revision and all projections. Duplicate blocks get new IDs and rewrite their internal private links; public chart/model/dataset IDs remain stable.

### Metric definition registry (NI-029)

The `metric_definitions` table is implemented by migration 0005 as the append-only registry of versioned metric definitions (`near_api.metrics.registry`): deterministic `uuid5(metric_id:version)` identity, name/unit/frequency/economic_scope/formula_key, a nullable `source_id` FK to `app.sources` (NULL only for explicitly gated definitions whose source does not exist yet — a recorded unavailability, never a fabricated attribution) and bounded definition/quality_rules JSONB. Registration (`register_definitions`) is idempotent and content-verified: an existing `(metric_id, version)` row diverging from the code registry is a registry error, because a registered definition can only be superseded by a new version, never edited. FORCE RLS with near_operator-only write policies and near_app read access; no UPDATE/DELETE grants for any role. The documented NI-028 interpretation is resolved by NI-031: migration 0007 (`0007_metric_chart_registries`) added the referential FK `dataset_metrics.metric_definition_id → metric_definitions(id)`, so staged datasets can only bind registered definition UUIDs and a manifest with an unregistered metric reference is rejected by the database (fail closed). Computed values are NOT duplicated here — they live in NI-028's `metric_observations` through the staging pipeline; NI-029 emits prepared manifests (`near_api.metrics.emit`, `python -m near_api.metrics build`) whose member metrics are registered definition UUIDs and whose observation values are exact Decimals explicitly quantized to the NUMERIC(78,30) storage scale with the exact string preserved in the observation quality metadata.

### Chart definition registry (NI-031)

The chart registry is implemented by migration 0007 as two append-only FORCE-RLS tables (`near_api.charts.registry`): `chart_definitions` holds one immutable row per `(chart_id, version)` with deterministic `uuid5(chart_id:version)` identity, title/description, a fixed category set (`activity/fees/treasury/supply/model`), a fixed visualization set (`line/area/bar/scatter/panels`), the honest `data_status` advertisement (`available`/`unavailable` with a mandatory recorded reason for unavailable charts), the expected `update_frequency`, bounded `allowed_ranges` (presets plus `max_days` ≤ 366 per CHART_SYSTEM), the supported-filter JSON Schema (closed object; string enums only, approved source/recipient/price-basis mappings), `unit_schema` (per-series units bound to the referenced metric definitions' units), the denormalized `metric_definition_ids` list, `source_lineage` (SRC ids that the bound definitions record plus a mandatory qualification note) and `renderer_version`. `chart_metrics` is the binding junction `(chart_definition_version_id, metric_definition_id, series_role)` with RESTRICT FKs into both registries; the bounded `series_role` values (`required_primary/required_secondary/required_x_axis/required_y_axis/optional_overlay/optional_context`) define required and optional series. A definition fully describes what renders — visualization, bindings, units, filters, ranges, renderer version — so adding a supported definition needs no new page implementation (`view_contract` derives the renderer-agnostic contract). Only `available` charts are advertised as live: a chart bound to a gated metric (`availability "G"`) must be registered `unavailable` with its OQ reason, and `near_api.charts.registry.validate_registry` fails closed on unknown metric references, unit mismatches, invalid filters/ranges/lineage and any divergence between stored rows and the code registry (`register_charts` is idempotent and content-verified like the metric registry; no UPDATE/DELETE grants exist, so a chart change appends a new version). The initial registry resolves the CHART_SYSTEM catalog against the real NI-029 inputs: seven available charts (intents-volume, gross-fees, observed-conversions, treasury-payouts, quantity-usd-sensitivity, supply-context, fee-volume-association) and four honestly unavailable ones (model-diagnostics — no published model artifact yet; protocol-revenue, capture-rate, fee-funded-buybacks — OQ-01/OQ-08/OQ-11 gates). Last-updated, data quality and actual date coverage stay with the resolved ChartView dataset (NI-032), never in the definition.

The dataset staging/publication zone above is implemented by NI-028 (`near_api.datasets`, migration 0004). Documented interpretations: `dataset_metrics.metric_definition_id` stores the opaque registered metric identifier until the `metric_definitions` registry lands (NI-031 adds its referential FK); `dataset_inputs.ingestion_run_id` is a reserved nullable column until the NI-030 ingestion-run lifecycle adds its FK; `dataset_versions.quality` JSONB accumulates `{"operator", "validation", "revision"}` stages written before approval; observation values use the derived-amount NUMERIC(78,30) convention with raw-precision originals retained in the hash-pinned manifest artifact; row-level reason metadata for null values lives in a bounded `metric_observations.quality` JSONB. Staging persists the version, member metrics, inputs and observations and runs validation in one advisory-locked transaction (committed status `validated` or `rejected`); identical semantic input deduplicates on `UNIQUE(dataset_key, content_sha256)`; publication is the single transaction that approves a validated version and switches the `active_datasets` pointer (trigger-enforced approved gate, same-key composite FK, revision delta in quality, superseded versions immutable and queryable forever). NI-027 imported archive files become `internal` artifacts with `imported/<batch_id>/<sha256>` storage keys whose bytes remain in the operator archive and are re-verified against `imported_files` before any staging read; manifest and copied input artifacts are content-addressed under `manifests/` and `blobs/` in operator storage, written before the transaction.

### Operator archive import zone (NI-027)

The read-only import of the existing research archive (implemented by `near_api.ingestion.archive`) writes four operator-zone tables before NI-028's artifacts/dataset tables exist. It stores metadata only — never file bytes — and the original archive stays untouched on disk:

- `sources` — the operator-managed `data_sources` catalog subset: stable `SRC-*` text PK, name, docs/base URLs, `access_status` disabled/documented/approved, `license_status` unknown/unverified/verified/prohibited, verified_at, bounded JSONB lineage. No secrets. Readable by near_app; writable by near_operator only.
- `import_batches` — one row per verified import. UNIQUE `manifest_sha256` is the idempotency key: re-importing the same manifest re-verifies every byte and changes nothing. Also records the cohort-registry hash, file count, verified byte total and importer identity.
- `imported_files` — PK (batch_id, relative_path); sha256, byte_size, `file_role` raw/aggregate/provenance/editorial/script, `coverage_scope` raw_saved_response/aggregate_window/partial_raw_audit/point_in_time_snapshot/process_documentation, half-open UTC `[coverage_start, coverage_end_exclusive)`, source FK, per-cohort license visibility and a ≤4 KiB sanitized metadata JSONB (URLs credential-redacted). Classification is deliberately conservative: a file is `raw` only when the archive itself documents it as a saved response/export, so aggregate-only cohorts can never claim raw-chain completeness.
- `source_runs` — retrieval lineage documented by cohort manifests (endpoint/job identity, retrieval UTC, byte count), the historical counterpart of `ingestion_runs`; the live ingestion lifecycle remains NI-028/NI-030 scope.

All four tables are FORCE RLS with near_operator-only policies; near_app has SELECT on `sources` only. Batch writes are all-or-nothing: any hash mismatch, missing/extra/symlinked file, undeclared cohort or checksum divergence rejects the whole batch before any row is written.

## Transactions, authorization and deletion

1. Verify JWT then start DB transaction, SET LOCAL identity using set_config; never interpolate untrusted SQL. API runtime role is not table owner and cannot bypass RLS. Every private query includes owner predicate as well.
2. Save locks documents row, checks expected revision, validates schema/references, resolves data pins once, writes version and projections, increments pointer/revision atomically. A mismatch returns 409 without changes.
3. Read historical version verifies parent document owner; knowing a version UUID grants no access. Public release content is a separate entity, never “document is public” on an ordinary private record.
4. Delete document: delete the owner-checked parent in one service transaction; ON DELETE CASCADE on document→versions→projections and document→export_jobs removes these children (handle deferrable current pointer; no general direct revision-delete endpoint). Owned snapshots/saved charts survive unless explicitly deleted; their source data remain globally immutable. Model/data/artifact scientific FKs use RESTRICT.
5. Delete user: explicit privileged retention workflow, purge documents/saved instances/private snapshots/exports/profile; global data and public editorial artifacts stay. Automated self-service deletion is P2; P0 settings explains operator-assisted removal. No silent orphaning.
6. Expired export bytes may be deleted after job expiry; document versions retain sufficient data/pins to regenerate. Scientific artifacts required by any approved dataset/published model/revision cannot be garbage-collected.

## Required migration verification

Empty DB → head, rollback last reversible migration, upgrade again; two-user RLS tests over pooled connections; race two identical revision saves; reject cross-owner snapshot/document refs, dangling evidence and out-of-range NUMERIC. Verify restoring a backup preserves content/artifact hashes. No DB trigger is a substitute for validating rich editor schema in the document service.

### NI-035 storage implementation

Migration `0011_saved_charts` applies FORCE RLS with active-identity checks, composite `(id,owner_id)` uniqueness, RESTRICT references to the immutable chart definition and last resolved dataset, and user-delete cascade. Selection/label/mode edits advance `updated_at`; resolution-only dataset telemetry does not. The runtime cannot update owner or definition columns. Instance deletion leaves the global registries/datasets intact.

### NI-044 storage implementation

Migration `0013_chart_snapshots` creates `app.research_snapshots` with the same FORCE RLS active-identity pattern and no UPDATE grant or policy for any role (rows are immutable once committed), plus the operator purge-only DELETE. It lifts the 0011 P0 gate: `saved_charts.mode` accepts `'snapshot'` under a pairing CHECK (`(mode='live') = (snapshot_id IS NULL)`) and `snapshot_id` gains the same-owner composite FK into `research_snapshots(id, owner_id) ON DELETE RESTRICT`, so a referenced snapshot cannot disappear and a cross-owner reference is rejected by the database even if a service check raced. The service checks references before delete (typed 409) and the FK is the backstop.
